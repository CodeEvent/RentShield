03Findings, with the receipts

Gap

E-signature status can lie forever

Once dispatched, nothing ever calls the provider again. getNotarizeStatus() exists in the API service but is called from zero places in the UI, and no inbound webhook receiver exists for DocuSeal/OpenSign. The badge shows whatever status came back from the first dispatch, permanently.

rentshield-api.service.ts · notarize_status_view (unused) · no webhook route in paperless/urls.py
Gap

A whole review-gate workflow nobody can trigger

Workflow #14 tags every certified-e-signature notice "Pending Review" at creation. Workflow #15 only clears it once a "Details Confirmed" custom field is ticked — but no screen in the app exposes that field to a property owner. The frontend already dispatches immediately on generation, bypassing this gate entirely. The tag just sits there, and the "Pending Review" / "Being Notarized" dashboards likely undercount or misrepresent what's actually happening.

create_rentshield_workflows.py · workflows #14 & #15 · "Details Confirmed" field
Gap

Notary status is a typo away from silently breaking

"RentShield: Notary Public Status" is a plain string field. Every place that reads it does an exact match against the lowercase literal "completed". Type "Completed", "done", or leave a trailing space, and the notice quietly never shows as finished anywhere — no error, no validation.

custom_fields.py · notary_status (STRING, not SELECT)
Gap

Nobody tells the landlord when either path finishes

The notary officer gets an intake email the moment a request comes in. The landlord gets nothing back — not on e-signature completion, not on notarization completion or rejection. The loop only closes if they happen to reopen the Notices list.

service.py · _notify_notary_fulfillment_requested() has no completion counterpart
Design note

Two "notarization" concepts, one confusing family of names

Certified E-Signature and Real Notary Public are priced and labeled as clearly different things on the pricing page — but their internal tags ("Being Notarized" vs "Awaiting Notary Public") and fields (add_notarization vs add_real_notarization) share enough vocabulary to blur together, especially since both can be selected on the same notice with no guidance on why you would.

04Ways to reshape this — pick any, none are built yet

1

Turn the status field into a real choice

Replace the free-text notary_status with a SELECT field (pending / completed / rejected), the same pattern RentShield: Reason and RentShield: Property Type already use. Closes the typo bug outright.

low effortcloses a real bug
2

Notify the landlord on completion, not just the notary on intake

Mirror _notify_notary_fulfillment_requested() with a completion email fired from wherever the status flips to completed/rejected — same reasoning as the existing "operational, not RBAC" fulfillment pattern, just closing the other end of it. Applies to both paths.

low-medium effortcloses the loop
3

Give e-signature status a heartbeat

A scheduled task that actually polls DocuSeal/OpenSign for in-flight notices and calls sync_notarization_stage_tag() — the same recurring-task shape the notary-provider research scanner already uses elsewhere in this codebase, just pointed at a different job.

medium effortreuses an existing pattern
4

Retire or finish the Pending Review gate

Either delete workflows #14/#15 and the two saved views that depend on them (dead weight the frontend already routes around), or actually build the missing piece: a real "confirm before we dispatch" screen, if that review step is still wanted on purpose.

needs a decision firstremoves dead weight either way
5

Make the two add-ons explain themselves, or block combining them

Either add a line of copy on the form clarifying when you'd want both (e.g. "certified signature now, physical notarization to follow"), or treat them as mutually exclusive choices in the UI if there's no real reason to pick both.

low effortclarity, not new logic
